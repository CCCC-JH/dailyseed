## 1. 后端

### 1.1 ★ Cookie 里存的是可枚举的 userId —— 那是一条能冒充任何人的凭据

**原样**：`SessionCookie.readUserId()` 把 Cookie 值 `Long.parseLong` 一下就当身份用；
`remember()` 写的是 `cookie(String.valueOf(userId))`。也就是说 `dailyseed_uid=5` 就等于"我是 5 号用户"。

**为什么这是真问题**：`HttpOnly` 只挡"脚本读它"，**完全不挡"用户自己编一个值"**。
一个自增整数是最容易被枚举的东西——遍历 1..1000 就能读到别人的花园、卡片、毕业记录。
原来那段注释把它解释成"不放任何秘密，所以安全"，**搞错了性质**：它不需要是秘密，
**它就是凭据本身**，凭据必须不可猜。

**改法**（`RecoveryTokenStore` + `V5__recovery_tokens.sql` + `SessionCookie`）：

- 浏览器侧：256 位 `SecureRandom` 随机令牌（64 位十六进制），每次响应 `Set-Cookie`
- 服务端：`recovery_tokens(token_hash PK, user_id, expires_at)`，只存 **SHA-256**，400 天到期
- 读：`findUserId(token)` 先按 `[a-f0-9]{64}` 卡格式，再查表 + 校验未过期
- 写：同一个 token 仍指向同一个人 → `renew()` 续期；换人 → **签发新令牌**（旧的留着自然过期）
- 明确**不接受旧版数字 Cookie**（不迁移）

**证据**：`verify_cookie.py` 第 18/19 条是照着攻击路径写的 —— 伪造"合法用户的数字 Cookie" → `400`；
伪造"格式合法但不存在的令牌" → `400`。**19/19 PASS**。

**通用判据**：凡是"客户端给什么、服务端就信什么"的地方都过一遍这个筛子——
**这个值如果是可枚举的标识符，那它就不能当凭据**。

### 1.2 「走过的」列表的 N+1 查询

`ExploredService.explored()` 原来对每条历史 `cards.findById(a.cardId())` 逐条往返 →
改成 `CardStore.findByIds(Collection)` 一次 `WHERE c.id IN (:ids)`（`JdbcClient` 会把集合展开）。

配套测试比实现更值得看：

```java
new CardStore(null) {
    @Override public Map<Long, Card> findByIds(Collection<Long> ids) { batches.incrementAndGet(); ... }
    @Override public Optional<Card> findById(long cardId) {
        throw new AssertionError("列表不应再逐张查询");   // ★ 退回去就炸
    }
}
...
assertThat(batches.get()).isEqualTo(1);
```

**把优化写成不变量**，而不是断言"结果一样"。

### 1.3 `UserStore.createAnonymous` 加 `@Transactional`

原来是 `insertUser()` + `INSERT INTO user_devices` 两条独立语句：第二条失败就留下一个**没有设备的孤儿用户**。

### 1.4 `graduate` 返回"实际发生了没有"

`App.tsx` 的 `graduate` 从 `Promise<void>` 改成返回 `Plant | null`；`Garden.tsx` 的
`confirmGraduate` 用返回值决定"关弹层 + 开分享卡"还是"什么都不做"。
旧代码在**毕业请求失败**时照样关弹层、并且拿**过期数据**去画分享卡。

## 2. 前端

### 2.1 ★ `catch` 被当成了"我知道这是什么错"

**原样**（`bootstrapDevice`）：

```ts
.catch(async () => {           // 任何异常都进这里
  const fresh = newDeviceId()  // 换一个新 deviceId……
  const info = await createSession(fresh)   // ……并建一个新账号
})
```

**后果**：一次瞬时断网（`TypeError`）、一次 503，都会被解释成"这个 deviceId 坏了" →
**用户的花园被换成一个空账号**。这是"最坏的一类 bug"：不报错、日志干净、只是数据没了。

**改法**：先判别，只有"我知道后端会这么回"的情况才走恢复：

```ts
if (!(error instanceof ApiError) || !((error.status === 400 && !id) || error.status === 401)) throw error
```

判据不是拍脑袋：后端 `SessionController.Request.deviceId` **刻意不加 `@NotBlank`**，
400 只在 `deviceId` 为空时抛（`"deviceId 不能为空（这台设备也没有可用的身份凭据）"`），
所以"400 且本地没有 id"正好等于旧代码想抓的那一种，其余一律不动身份。

同类还有两处：

- `booting = null`（**失败的 Promise 不能进缓存**，否则"再试一次"永远拿到同一张失败票）
- `repairing` 失败要 `delete(badId)`（同上）

**证据**：`qa-verify-bootstrap.mjs` 里 `network` / `server` 两种故障各一条场景：
故障时**身份一个字节都不许变**，恢复后重试成功。

### 2.2 一页一个错误态

`garden` / `explored` 原来共用全局 `phase` / `error`，而且：

```ts
catch (e) { if (!(e instanceof ApiError && e.status === 401)) fail(e) }   // 401 被静默吞掉
```

花园挂了会把整页拖进错误屏，401 连痕迹都没有。现在各自 `gardenPhase` / `gardenError`，
降级为"这一页没加载出来"，其余页面照常。

### 2.3 弹层做成"栈"

原实现每个弹层各自监听 Esc、各自保存/恢复 `body.overflow`、各自抢焦点。
两个弹层叠着时：一个 Esc 把两个都关了；内层关闭会把 overflow 恢复成"没锁"。
新实现用一个模块级 `openSheets` 数组：只有**栈顶**响应 Esc/Tab，body overflow 只在
**第一个打开**时保存、**最后一个关闭**时恢复，关闭后把焦点还给打开它的那个元素，
Tab 在层内循环。另外把 `onClose` 放进 ref，effect 依赖只剩 `[open]`
（父组件每次渲染都重装监听是 React 里最常见的隐性抖动源）。

### 2.5 视觉：深色 → 米白纸张

`#06070a`/`#0f1115` → `#f8f7f2`；manifest 的 `theme_color`/`background_color`、
`apple-mobile-web-app-status-bar-style`（`black-translucent` → `default`）、
毕业分享图（`shareCard.ts` 整套配色）、时间控件的 `filter: invert(0.75)`（深色时代的产物，
在浅色底上会让图标看不见）**都跟着改了**——这一串如果漏一个，就会出现"白底白图标"这种低级问题。

`.navigation > .brand` 在手机上 `position: absolute`（当页头）、960px 起在侧栏里 `position: static`。

> ⚠️ 产品设计文档**没有规定配色**，所以这是自由设计选择；但它是**产品级**决定，不是纯技术改动。
> 另外 `--serif` 在中文 Windows 上会落到**宋体**，大标题是"书页感"还是"过时"要在真机上看一眼。

## 4. 记下但这一轮**没有**改的

| 项 | 说明 |
| --- | --- |
| `recovery_tokens` 无界增长 | 实测：同一 `deviceId`、不带 Cookie 连发 3 次 `POST /api/session` → **3 行**（正常浏览器会 `renew`）。清理只在签发时、只清该用户的已过期行（400 天）。建议加"每用户保留上限"或定期清理 |

| 前端回归场景 20 → 9 | 换成"跑真源码"方向更真，但**条数掉下来了**：旧版声明的 20 条里有些（如更细的并发/守卫组合）没有对应实现，这一轮只补回了 4 道守卫与 2 个场景 |

### 6.2 截图上看出来的两处

- **侧栏那句被 `<br/>` 挤断**成「生活会长出自己的样／子。」：可用宽度 = 240 − 26×2 − 12×2 = **164px**，
  而那句话第二行 10 个汉字 × 16px = **160px**，只余 **4px** —— 字体一回退就断。→ note 的左右 padding 12 → 8px（可用 172px）。
- **桌面端"只变宽、没变构图"**：卡片内宽 ≈670px，插画固定 230px（占 34%）；
  而卡背上最宽的一行字（23px × 12 字 ≈ 276px）本来就比插画宽。→ ≥960px 时插画 300px（**图比最宽的文字略宽**），
  两面 `min-height` **同步** 400 → 440px（不同步就会在翻面末段跳高）。

### 6.3 这一轮新增的"仪器"

- `tools/verify_redlines.py --style`：9 条样式断言 + 7 条自检（含正反例：黑/白必须 21:1、同色必须 1:1、差 1/255 要报、差 40/255 要放过）。
  第 9 条是**产物同步**（dist 的 CSS 里读不到当前令牌 = 改了样式忘了 build）——**它本身也做过反例测试**：
  故意把 dist 里那个色改回旧值，它立刻报红；还原后转绿。
- 两个**实测过的假结论**（都写进脚本注释了，这类"仪器自己错"比被测对象错更危险）：
  ① 扫颜色前**必须剥掉 CSS 注释**——否则注释里那句"原来是 #73776b"会被当成"这个色还在用"，修完仍然报红；
  ② 自检行的判据是 `bool(hits) == want_hit`，而**非空列表恒为真**——第一版写成 `[False]` 让四条自检空转（当场被抓）。
- `docs/review-20261011/视觉规范.md`：把上面这些从"我的分析"变成"下一轮改样式时的判据"。
